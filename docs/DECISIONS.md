# Focus Quest 제품·기술 결정

## 2026-07-28 - Safe PDF storage object keys

- Keep the user's original PDF file name only in `study_materials.file_name`.
- Store every PDF under the ASCII-only key `<user UUID>/<material UUID>/source.pdf`.
- This preserves per-user RLS folder isolation while avoiding object-key failures caused by Unicode or special characters.
- Convert Supabase Storage status and policy failures into actionable user messages without exposing credentials or internal response bodies.
- Treat a successful analysis update as complete without requiring PostgREST to return the full JSON row.
- Remove NUL characters before writing PDF-derived analysis to PostgreSQL JSONB.

## 2026-07-26 — 계정 전환 시 로컬 기록 격리

### 결정

- 브라우저의 현재 로컬 상태에는 마지막으로 연결된 Supabase 사용자 ID를 소유자 표식으로 함께 저장한다.
- 게스트 상태는 소유자 표식이 없을 때만 첫 로그인 계정으로 병합한다.
- 다른 계정으로 전환하면 이전 계정의 로컬 기록을 새 계정으로 병합하지 않고, 새 계정의 클라우드 상태부터 불러온다.
- 로그아웃 전 마지막 변경을 저장하며, 저장 실패 시 로그아웃을 중단해 기록 손실을 피한다.
- 로그아웃 후 계정 기록은 공용 화면에서 제거하고, 같은 계정으로 다시 로그인하면 클라우드에서 복구한다.
- 클라우드 저장 비활성화 표식도 사용자별로 구분해 한 계정의 삭제 선택이 다른 계정에 영향을 주지 않게 한다.

### 이유

- RLS가 서버 행을 격리해도, 같은 브라우저의 공용 LocalStorage를 그대로 재사용하면 A 계정의 기록이 B 계정으로 업로드될 수 있다.
- 공유 기기에서는 로그아웃 후에도 이전 계정 기록이 화면에 남는 것 자체가 개인정보 노출이 될 수 있다.
- 다기기 동기화 중 발생한 마지막 변경이 저장 큐에 남은 채 로그아웃되면 복구 시 최신 상태가 누락될 수 있다.

## 2026-07-26 — 공개 배포 인증 안정화

### 결정

- Cloudflare OAuth는 Codex 내장 브라우저에서 열지 않는다.
- `wrangler login`은 일반 Windows 터미널에서 실행하고 운영체제 기본 브라우저로 승인한다.
- OAuth 콜백은 한 번에 하나만 실행하며, 60초 이상 진전이 없으면 해당 Wrangler 프로세스와 콜백 포트만 확인해 종료한 뒤 다시 시도한다.
- 인증이 끝난 뒤에는 `wrangler whoami`로 계정을 먼저 확인하고, 배포 명령은 별도 비대화형 프로세스로 실행한다.
- 기존 Sites 프로젝트 ID와 Git 이력은 유지하며, 공개판은 Supabase Auth와 별도 Cloudflare Worker 주소를 사용한다.

### 이유

- 2026-07-26 Cloudflare OAuth 화면을 Codex 내장 브라우저로 여는 동안 내장 Chromium의 GPU 프로세스가 종료되고 재실행에도 실패해 Codex 앱이 복구됐다.
- 같은 시도에서 Wrangler OAuth 대기가 만료된 뒤 Windows 비동기 핸들 오류도 발생했다.
- Focus Quest 빌드, Supabase 연결, Git 상태 및 시스템 메모리에서는 앱 종료를 설명할 오류가 발견되지 않았다.
- Sites의 현재 접근 정책은 소유자 또는 워크스페이스 사용자 범위이므로, 일반 사용자에게 공개하려면 별도 공개 배포가 필요하다.

## 2026-07-26 — 공개 사용자 인증과 저장소

### 결정

- 일반 사용자용 인증은 Supabase Auth의 이메일·비밀번호를 기본으로 사용한다.
- Google 로그인은 Supabase 제공자 설정이 끝난 환경에서만 노출한다.
- 공개 운영 데이터는 Supabase Postgres의 `focus_quest_cloud_states`에 저장한다.
- 모든 사용자 데이터 접근은 `auth.uid() = user_id` RLS로 제한한다.
- 브라우저에는 publishable/anon key만 사용하고 `service_role` 키를 사용하지 않는다.
- 기존 Sites·ChatGPT 인증과 D1은 공개판 검증 전까지 소유자 전용 호환 경로로 유지한다.
- 첫 로그인 시 현재 기기의 로컬 기록을 새 공개 계정으로 병합한다.
- 공개 앱은 Cloudflare Worker와 Static Assets로 배포한다.

### 이유

- 현재 Sites 접근 정책은 워크스페이스 외부 계정을 허용하지 않는다.
- 인증·비밀번호·이메일 확인을 직접 구현하는 보안 위험을 피한다.
- RLS로 클라이언트에서 접근하더라도 사용자별 데이터 경계를 데이터베이스에서 강제할 수 있다.
- 기존 Phaser와 Vinext 구조를 다시 만들지 않고 공개 호스팅으로 이동할 수 있다.

### 비목표

- 이번 단계에서 과목·퀘스트·PDF 데이터를 구현하지 않는다.
- 자체 비밀번호 해싱과 자체 인증 서버를 만들지 않는다.
- 기존 D1 데이터를 이메일만으로 자동 연결하지 않는다.

### 재검토 조건

- 과목과 PDF가 추가되어 JSON 한 행 구조로 조회·보존 정책을 충족하지 못할 때
- 한국 사용자 대상 소셜 로그인 요구가 확인되어 Kakao·Naver가 우선순위가 될 때
- 유료 서비스의 데이터 위치·백업·탈퇴 요건이 확정될 때

## 2026-07-26 — 계정과 클라우드 저장 1차 방식

### 결정

- 공개 화면과 게스트 사용을 유지한다.
- 1차 계정은 Sites가 제공하는 선택형 ChatGPT 로그인을 사용한다.
- 로그인 사용자의 설정과 완료 기록은 Cloudflare D1에 저장한다.
- 데이터베이스에는 원문 이메일 대신 정규화한 이메일의 SHA-256 식별값을 저장한다.
- 로컬 기록과 클라우드 기록은 세션 ID로 중복을 제거해 병합한다.
- 클라우드 저장은 버전 번호를 사용해 동시 수정을 감지하고 한 번 자동 병합한다.
- 진행 중 세션에는 별도의 변경 시각을 기록하고, 여러 기기에서는 가장 최근의 시작·일시정지·재개·종료 상태를 적용한다.
- 로그인된 화면은 10초 간격과 창 재활성화 시점에 다른 기기의 변경을 확인한다.
- 같은 집중 세션이 두 기기에서 동시에 완료되어도 결정적인 세션 ID로 완료 기록을 한 번만 남긴다.
- 클라우드 기록 삭제 시 현재 기기의 로컬 기록은 보존하고 자동 동기화를 끈다.

### 이유

- 현재 호스팅 환경에서 별도 OAuth 비밀키 없이 실제 사용자 식별이 가능하다.
- Google 또는 이메일 인증을 미완성 화면만 만든 상태로 남기지 않는다.
- 기존 게스트 경험과 타이머를 로그인 뒤에 가두지 않는다.
- 이후 과목·퀘스트 데이터가 추가되어도 같은 사용자 소유권 구조를 확장할 수 있다.

### 이번 단계의 비목표

- Google OAuth와 이메일 인증
- PDF 원본 저장과 R2
- 과목·퀘스트 데이터 동기화
- 운영 배포

### 재검토 조건

- 독립 도메인과 외부 OAuth 운영 주체가 확정될 때
- ChatGPT 계정이 없는 사용자가 핵심 고객 검증에서 유의미하게 확인될 때
- 과목·퀘스트 데이터 모델을 구현할 때 클라우드 상태 JSON을 개별 테이블로 분리할 필요가 생길 때

## 2026-07-28 — PDF 분석은 로컬 추출 + 비공개 원본 저장 + 서버 분석으로 분리

- PDF 원본은 Supabase Storage의 사용자 전용 비공개 경로에 저장한다.
- 텍스트 추출은 브라우저에서 수행해 Worker의 PDF 파싱 부하와 원본 전송을 줄인다.
- 분석 API는 Supabase 액세스 토큰을 다시 검증하며, 클라이언트가 보낸 사용자 ID를 신뢰하지 않는다.
- AI 출력은 구조화 스키마로 제한하고 다시 정규화한다.
- AI 키가 없거나 호출이 실패해도 기본 분석으로 전체 수동 퀘스트 흐름을 유지한다.
- AI 제안은 자동 확정하지 않으며 사용자가 수정하고 선택한 항목만 퀘스트로 등록한다.
- OCR, 다중 파일 일괄 분석, 적응형 추천은 이번 범위에 포함하지 않는다.

## 2026-07-30 — 첫 화면은 타이머 중심의 빠른 시작으로 운영

- 첫 화면의 주 행동은 `오늘 끝낼 한 가지 입력 → 10·25·45분 선택 → 즉시 집중`으로 한다.
- 최근 선택한 모험 친구와 추천 집중 소리는 유지하되, 친구 변경과 세부 시간·휴식·소리 설정은 보조 행동으로 둔다.
- 집중 목표는 진행 중 화면, 완료 화면, 최근 기록에 함께 표시한다.
- 작성 중 목표는 기기에 임시 저장하고, 시작한 목표와 완료 기록은 기존 계정 동기화 데이터에 포함한다.
- 입력이 비어 있으면 시작을 막지 않고 `자유 집중`으로 기록한다.
- 과목·퀘스트·PDF 기능은 삭제하지 않고 첫 집중 이후 필요할 때 사용하는 확장 기능으로 유지한다.

### 이유

- 타이머의 핵심 가치는 계획을 많이 세우는 것보다 빠르게 집중을 시작하는 데 있다.
- 첫 화면에서 캐릭터를 먼저 고르게 하면 해야 할 일을 입력하고 시작하기까지 단계가 늘어난다.
- 목표를 기록과 함께 남기면 단순 누적 시간보다 실제로 무엇을 했는지 되돌아보기 쉽다.

## 2026-07-30 — 모험 세계관과 첫 화면 배경을 하나로 연결

- 등산은 `산길잡이 모리 · 해오름 봉우리 · 정상 깃발`, 수영은 `유적 잠수부 나루 · 유리산호 유적 · 황금빛 보물상자`, 낚시는 `전설 낚시꾼 보리 · 달비늘 호수 · 황금 잉어`로 정의한다.
- 이름은 한 번에 읽히는 두세 음절과 장소의 핵심 풍경을 조합하고, 설명은 캐릭터의 행동과 완료 사건을 한 문장 안에 담는다.
- 첫 화면은 집중 장면에서 사용하는 기존 고해상도 픽셀 배경을 그대로 재사용한다.
- 모험 선택지는 숨겨진 설정 대신 항상 보이는 `모험 지도`로 제공하되 빠른 시작보다 시각적 우선순위는 낮게 유지한다.
- 다른 게임은 분위기와 정보 전달 방식만 참고하며 고유 캐릭터·지명·그래픽은 복제하지 않는다.

### 이유

- 시작 화면과 집중 장면의 배경이 다르면 캐릭터가 같은 세계를 여행한다는 감각이 끊긴다.
- 역할·장소·완료 사건이 분명하면 장황한 설명 없이도 사용자가 원하는 모험을 고를 수 있다.
- 이미 완성된 원본 배경을 재사용하면 새 에셋 생성 없이 품질과 세계관 일관성을 동시에 높일 수 있다.
